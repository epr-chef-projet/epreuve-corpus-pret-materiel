# Contrats publics et dépendances d'intégration

**Version 1.13 - contrats d'intégration.** [Architecture](../../cahiers-des-charges/technique/architecture-contrats.md) et [transactions](../../cahiers-des-charges/technique/transactions-etats.md) possèdent les choix de conception ; ce document possède les formes exactes. Les sections distinguent les capacités disponibles de celles encore prévues. Une signature documentée ne constitue pas, à elle seule, une preuve d'implémentation ou de qualification.

<a id="vocabulaire"></a>

## 1. Vocabulaire et réception

| Élément     | Contrat                                                                                                                                                                        |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Identifiant | UUID opaque, chaîne canonique minuscule ; génération UUIDv7 côté serveur. `operationKey` est un UUID créé pour une intention, conservé pour ses reprises.                      |
| Version     | Entier `1..2147483647`, nombre JSON sûr ; saturation refusée, aucun retour à zéro. `expectedVersion` obligatoire pour modifier une ressource existante.                        |
| Quantité    | Ligne `1..999999` ; total `0..999999`. Demande ≤100 lignes uniques ; brouillon vide admis, confirmation/remplacement non vides.                                                |
| Texte       | Nom 1..120, catégorie 1..80, description nullable ≤2000, motif d'équipe 1..500 ; caractères Unicode, espaces extérieurs retirés. Description vide normalisée en null.          |
| Recherche   | Fragment littéral du nom ≤120 caractères, insensible à la casse ; catégorie facultative, correspondance exacte. Aucun joker SQL fourni par le client.                          |
| Navigation  | `page` entier de 1 à 9007199254740991 (représentation JSON exacte) ; `perPage` défaut 25, maximum 100. Filtres modifiés : page 1. Pas de total global obligatoire.             |
| Instant     | ISO 8601 UTC, précision milliseconde, suffixe `Z`. `observedAt` indique l'heure de préparation de la projection ; ce n'est ni une version ni une promesse d'actualité.         |
| États       | Demande : `draft`, `pending`, `accepted`, `handed_over`, `returned`, `rejected`, `cancelled`. Image/document : `pending`, `ready`, `failed`. Référence : `active`, `archived`. |

Les clés inconnues sont rejetées. Entiers JSON ou chaînes décimales de chiffres, après retrait des espaces extérieurs, sont admis puis normalisés ; booléens, fractions et notation exponentielle sont refusés. UUID, états et versions sont validés avant construction. Acteur, rôle et atelier ne sont pas des champs de commande du navigateur.

<a id="capacites"></a>

## 2. Capacités PHP publiques

`ActorContext` est produit par IdentityAccess depuis la session valable : `actorId`, `workshopId`, `role: borrower|staff|manager`. Il ne remplace pas les contrôles de droits courants. Les DTO sont des valeurs sans accès différé ; chaque signature métier reçoit ce contexte serveur. Les jobs utilisent un `ServiceContext` distinct, construit depuis la capacité configurée et le routage contrôlé des effets : aucune session humaine inventée ni privilège hérité du rôle du demandeur. `Page<T>` contient `items`, `page`, `perPage`, `hasMore` et `observedAt`, avec liste dense ordonnée.

| Propriétaire / capacité                     | Entrée → résultat                                                            | Préconditions et sens                                                                                                                                     |
| ------------------------------------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| IdentityAccess / `ResolveActor`             | Session → `ActorContext`                                                     | Authentification et contexte fiable selon [sécurité](../../cahiers-des-charges/technique/donnees-securite.md), aucun atelier choisi par le client.        |
| Catalog / `ReadEquipmentPage`               | Recherche, catégorie, page, taille, audience → `Page<EquipmentData>`         | Tri nom puis UUID ; actif pour catalogue de prêt, archivés seulement pour gestion responsable.                                                            |
| Catalog / `ReadEquipmentBatch`              | ≤100 UUID distincts → liste `EquipmentData`                                  | Lecture du même atelier ; manque/hors atelier indistinguables, sans données étrangères.                                                                   |
| Catalog / `LockEquipmentBatch`              | ≤200 UUID distincts → liste `EquipmentState`                                 | Transaction active et même contexte ; ordre UUID global ; protection conservée jusqu'au commit extérieur. Borne 200 réservée à l'union d'un remplacement. |
| Catalog / `ReplaceTotalWithinUnit`          | UUID, total, version attendue, `minimumCommittedQuantity` → nouvelle version | Responsable ; référence protégée sur la même connexion ; minimum fourni par WorkshopOperations depuis les engagements protégés, total ≥minimum.           |
| Lending / `ReadCommitments`                 | ≤100 UUID distincts → `CommitmentTotals[]`                                   | Agrégat de tous les engagements de l'atelier, via capacité SQL étroite possédée par Lending ; aucun prêt, auteur ou historique retourné.                  |
| WorkshopOperations / `ReadEnrichedCatalog`  | Filtres/page/audience → page autorisée                                       | Composition dans un instantané commun court ; absences d'engagement valent zéro.                                                                          |
| WorkshopOperations / `ChangeEquipmentTotal` | UUID, total, version attendue, clé d'opération → `CommandReceipt`            | Action extérieure atomique appelant Catalog et Lending ; aucun SQL voisin.                                                                                |

`EquipmentData/State` : `equipmentId`, `name`, `description`, `category`, `totalQuantity`, `status`, `equipmentVersion`, `image: ImagePublishedData|null`. Image publiée : `imageId`, `generation`, `thumbnail` et `detail`, chacun `{url,width,height,mimeType:"image/webp"}` ; les dimensions vérifiées sont stockées à la publication, les URLs sont des routes privées. `CommitmentTotals` : `equipmentId`, `reservedQuantity`, `handedOverQuantity`. Ces données intermodules ne sont pas exposées intégralement au navigateur. Les appels d'agrégat portant sur une union de 200 sont fractionnés en lots ≤100. Les exceptions publiques utiles sont celles de la section erreurs.

### Accès et unités SQL utilisables

`IdentityAccess/PublicApi/ResolveActor::handle(Request)` produit le contexte depuis la session serveur revalidée, y compris lors d'un appel direct. `AuthorizeActor::handle(context, ability)` recontrôle l'identité courante et applique les capacités fermées `borrow`, `operate-loans`, `manage-catalog` ; une capacité inconnue est refusée. Les Gates HTTP utilisent la même matrice. Les actions des consommateurs peuvent ainsi autoriser un contexte sans importer le modèle interne d'utilisateur. `CatalogServiceProvider` enregistre explicitement `EquipmentPolicy`. Les actions et capacités Catalog revalident le contexte avec `AuthorizeActor` dans leur unité SQL, puis appellent Gate avec ce contexte explicite. La policy pure reçoit un utilisateur Laravel nullable et le contexte revalidé en argument supplémentaire ; elle applique la matrice publique `Role` et le périmètre de la ressource, sans résolution ni lecture SQL.

`App\Modules\IdentityAccess\PublicApi\SqlUnit::forActor(context, closure)` ouvre l'unité sur la connexion métier `pgsql` (connexion logique `app` du CDC), vérifie l'identité courante et établit les paramètres PostgreSQL locaux avant le travail. Cette capacité appartient à IdentityAccess, qui possède la résolution de l'autorité et son établissement SQL ; les consommateurs passent par son API publique. `forActor(ActorContext, Closure(): void): void` appelle le travail sans argument et ne retourne aucune valeur. Le cas d'usage propriétaire constitue son résultat matérialisé ; la capacité ne lui transmet ni connexion, ni modèle, ni builder, ni chargement différé. L'unité fixe localement `lock_timeout=2s` et `statement_timeout=5s` ; elle n'effectue pas de rejeu automatique. Les repositories participants appellent `assertActor(connection, context): void` avant leur premier accès protégé, en fournissant leur propre connexion ; cette garde refuse absence de transaction, autre connexion ou contexte différent. Une unité imbriquée ne change pas silencieusement d'atelier, d'acteur ou de capacité.

`forActorRead(ActorContext, Closure(): void): void` ouvre seul un instantané `REPEATABLE READ, READ ONLY`, avant toute lecture, avec une durée SQL de 5 s. Il établit le même contexte serveur et recontrôle l’identité. Dans une unité déjà active, il vérifie contexte et connexion puis participe sans modifier l’isolation ni ouvrir une transaction indépendante. Le contrat sans argument ni résultat de la closure reste identique ; les lectures produisent des valeurs matérialisées.

`ReadEquipmentPage::handle(ActorContext, EquipmentQuery): EquipmentPage` et `ReadEquipmentBatch::handle(ActorContext, list<string>): list<EquipmentData>` sont disponibles dans `Catalog/PublicApi`. `EquipmentQuery` contient `search`, `category`, `page`, `perPage`, `audience: catalog|catalogManagement`. L’audience de gestion recontrôle le droit responsable ; l’autre ne retourne que les références actives. Le lot peut identifier des références archivées pour des lignes existantes autorisées, sans endpoint navigateur permettant de découvrir les archives. `EquipmentData` expose exactement `equipmentId,name,description,category,totalQuantity,status,equipmentVersion,image`. Les types imbriqués d’image sont publics ; `image` vaut actuellement null, faute de producteur d’image. `EquipmentPage` contient les cinq champs de page décrits ci-dessus. Aucun calcul de disponibilité ne fait partie de ces capacités. `LockEquipmentBatch::handle(ActorContext, list<string>): list<EquipmentState>` et `ReplaceTotalWithinUnit::handle(ActorContext, equipmentId: string, totalQuantity: int, expectedVersion: int, minimumCommittedQuantity: int): int` sont disponibles. Ils participent uniquement à une unité extérieure `pgsql`, active, en `READ COMMITTED` et inscriptible, avec le même contexte courant ; ils n'ouvrent pas une transaction indépendante. `EquipmentState` est immuable, possède les huit mêmes champs sélectionnés que `EquipmentData` et n'expose aucun accès différé.

Le lot de protection accepte une liste dense de 0 à 200 UUID canoniques distincts, rend les seules références du même atelier, ordonnées par UUID, et omet de façon identique absence et atelier étranger. Il relit après acquisition. Les protections restent acquises jusqu'à la fin de l'unité extérieure. Une trace PostgreSQL locale à la transaction relie les UUID réellement protégés à cette unité et à son contexte ; elle suit aussi le rollback des savepoints. Un appel complémentaire ne peut ni dépasser 200 références ni acquérir un nouvel UUID inférieur à ceux déjà protégés. Libérer un savepoint conserve les protections ; son annulation retire celles qu'il a acquises. Cette garde de protocole interne ne remplace ni l'autorisation ni RLS.

Le participant de total exige le droit responsable courant et une protection préalablement acquise par `LockEquipmentBatch` sur cette même connexion. Il contrôle les bornes, la version attendue, le minimum protégé fourni par WorkshopOperations et la saturation ; il écrit total/version/date puis programme l'invalidation après commit extérieur. Il ne lit aucun engagement Lending, n'ouvre aucun endpoint et ne possède pas le reçu de la commande transverse. L'orchestrateur fournit un minimum actuel sous les protections communes, conserve sa transaction et laisse remonter tout refus pour annuler l'unité concernée. Les courses avec les prêts et engagements réels restent à qualifier lors de leur raccordement.

Pour ces deux participants, une entrée malformée produit `InvalidArgumentException` ; une unité, un contexte ou un protocole de protection incorrect produit `LogicException`. Un acteur devenu invalide ou sans droit requis produit `Illuminate\Auth\Access\AuthorizationException`. Le lot omet les références absentes/étrangères ; le participant de total ne révèle pas cette distinction et peut produire `Illuminate\Database\Eloquent\ModelNotFoundException` si la référence protégée n'est plus admissible. Les refus métier du total sont `Catalog\PublicApi\Errors\ContentConflict`, `TotalBelowCommitments` et `VersionExhausted`. Une erreur SQL reste une erreur de l'unité extérieure : l'orchestrateur possède son annulation et sa politique de reprise bornée.

`forService(ServiceContext, Closure(): void): void` suit le même contrat de travail sans argument ni résultat et exige l'identité et la capacité configurées du processus (`IDENTITY_SERVICE_ID`, `IDENTITY_SERVICE_CAPABILITIES`), sans rôle utilisateur. Aucun droit de service n'est activé par défaut dans HTTP. La seule capacité introduite pour les sessions est `identity_access.publish` ; les futures capacités de traitement doivent être ajoutées avec leurs usages et preuves.

`AdmitSessionPublication::handle(service, actorId, role, broadcastToken)` est réservé au producteur ayant déjà établi l'audience autorisée depuis sa source métier. Il ne recherche pas des destinataires à partir d'une demande navigateur. Il rend `null` ou `{channel,authGeneration}` après vérification du même atelier, du compte/rôle courant, de l'expiration/révocation et de la session vivante via le handler Laravel configuré. Il partage le verrou de la ligne de session avec la révocation : une admission acquise avant celle-ci peut déjà être engagée ; aucune nouvelle admission après sa validation. Le résultat est destiné à la publication immédiatement admise, pas à un cache de routes réutilisables. Aucun identifiant de session ni ciphertext n'est transmis au publisher. L'abonnement navigateur et la qualification du socket maintenu après sortie complètent ce contrat avec le cadre frontend.

`ReadSessionCandidates::handle(ServiceContext, roles, actorId?, cursor?, limit=100): SessionCandidatePage` reçoit une audience déjà autorisée par le producteur : liste dense non vide de `Role`, sans doublon, compte facultatif et limite de 1 à 100. `SessionCandidatePage` contient `candidates: list<SessionCandidateData>` et `nextCursor: string|null` ; chaque candidat est `{actorId,role,broadcastToken}`. Les valeurs sont matérialisées et immuables, sans accès différé. Le curseur opaque est lié à l'atelier et à cette audience ; une page pleine peut donner un curseur suivi d'une page vide. Modifier l'audience recommence sans curseur. Ces candidats restent provisoires : appeler immédiatement `AdmitSessionPublication` pour chacun avant l'envoi. Aucune liste de tokens sérialisée dans un job ne fait autorité.

La fonction PostgreSQL `identity_access_session_candidates(jsonb,uuid,uuid,integer)` est possédée par IdentityAccess, avec index `(workshop_id,id)`, contexte de service local, bornes et droits d'exécution étroits. Elle sélectionne uniquement les sessions SQL non révoquées et non expirées du même atelier et des rôles courants demandés. Redis et la sérialisation avec la révocation relèvent de l'admission suivante. La capacité `identity_access.publish` est attribuée au seul processus Horizon de notifications, jamais implicitement au processus HTTP.

<a id="commandes"></a>

## 3. Commandes et résultats HTTP

La prop `auth.user` est nulle pour un invité. Pour le compte courant, `IdentityAccess/Identity/Data/AuthenticatedUserData` expose uniquement `id`, `login`, `displayName`, `workshopId`, `workshopName` (chaînes) et `role` (`borrower|staff|manager`). Ces six propriétés sont `readonly` après construction ; un changement produit une nouvelle valeur. La classe conserve l'héritage Laravel Data, la sérialisation explicite sans SQL et la génération TypeScript depuis sa déclaration PHP. Ce DTO de présentation n'est ni une autorité fournie par le navigateur ni un modèle public intermodule.

`GET /access/context`, route `access.context`, renvoie `SessionContextData` : `{user,broadcastToken,authGeneration,expiresAt,locale}`. Pour un invité les quatre premiers champs sont null ; pour une session valable, `user` conserve exactement les six champs ci-dessus, `broadcastToken` est une chaîne hexadécimale de 64 caractères, `authGeneration` un entier positif et `expiresAt` un instant UTC à millisecondes. Les mêmes métadonnées accompagnent `auth` dans les props Inertia, sans ajouter de propriété à `AuthenticatedUserData`. Le token opaque sert uniquement au routage ; aucun identifiant de session ni ciphertext ne sort. La réponse porte `private, no-store`. `locale` suit le seul en-tête de présentation contrôlé `X-Presentation-Locale: fr|en`, avec défaut français ; cet en-tête ne confère aucun droit.

`POST /broadcasting/auth`, route `broadcasting.auth`, utilise l'autorisation Laravel native, la session courante et CSRF pour `private-epr.session.{broadcastToken}`. Un token étranger ou une session invalide est refusé. La connexion transporte l'événement `.epr.notification` dans Echo ; la confirmation d'abonnement est distincte de la relecture HTTP. L'export frontend limité `resources/js/modules/identity-access/public/access.ts` fournit le cadre d'accès et l'acquisition/libération d'un consommateur de session. Ce dernier capture avant confirmation et avant lecture, puis active une vue seulement si son contexte et son buffer sont encore valides. Chaque propriétaire valide son payload concret et possède sa projection, sans import des éléments internes d'un voisin.

Toutes les commandes métier reçoivent `operationKey` ; les identifiants de route sont contrôlés dans le contexte courant. Le corps de création d'un brouillon comporte `items: [{equipmentId, quantity}]`. Sauvegarde de brouillon et remplacement transmettent la liste complète et `expectedVersion` ; retrait signifie omission explicite dans cette proposition complète. Confirmation transmet `expectedVersion` et `locale: fr|en`, fixée uniquement lors de la première réussite. Connexion/déconnexion conservent leur contrat de session distinct.

Acceptation, remise et retour transmettent version et clé. Refus et annulation d'équipe ajoutent `reason` ; annulation de l'auteur ne le demande pas. Suppression vise seulement un brouillon. Création/édition Catalog utilisent les champs décrits en section 1 ; création reçoit un total initial sans engagement, édition textuelle ne peut changer le total. Actif/archivé et changement du total sont des commandes séparées. Réception, retrait et reprise d'image, ainsi que reprise du document, suivent leurs contrats de [fichiers](../../cahiers-des-charges/technique/traitements-fichiers.md).

`CommandReceipt` contient `operationKey`, `operationType`, `resourceType: equipment|loanRequest|equipmentImage|loanDocument`, `resourceId`, `resultVersion`, `recordedAt`, et `replayed`. Le type d'opération appartient à une liste fermée déclarée par module, préfixée `catalog.`, `lending.` ou `workshop_operations.` ; il identifie la commande précise, jamais une classe libre. Le reçu atteste l'effet initial ; une lecture autorisée retrouve ensuite l'état actuel. Supprimer un brouillon conserve son reçu et sa dernière version supprimée. `ReadOperationResult(type, clé)` rend `applied` avec reçu ou `notEstablished`. L'absence ne prouve pas un échec : seule une reprise explicitement coordonnée, avec même clé/contenu et acquisition atomique, peut départager un appel initial encore actif ; jamais une nouvelle clé pour contourner l'incertitude.

Les commandes de gestion disponibles sont `catalog.equipment.create`, `catalog.equipment.update_text`, `catalog.equipment.archive` et `catalog.equipment.reactivate`. `Infrastructure/Operations` possède `OperationScope`, `OperationRepository`, `CommandReceipt` et `ReadOperationResult` : coordination technique sans import de module. La portée unique est atelier, acteur, type et clé ; le verrou consultatif transactionnel précède le verrou de référence. L’empreinte porte le contenu normalisé et la version attendue lorsqu’elle existe. Mutation et reçu final immuable sont acquis ensemble. Une répétition autorisée rend le reçu initial sans réappliquer l’effet, même si la référence a évolué ensuite. Les reçus ne contiennent ni texte ni corps HTTP et ne sont pas purgés par un TTL.

Les endpoints automatiques `access.context`, `broadcasting.auth`, `catalog.page`, `catalog.detail` et `catalog.operation` utilisent explicitement `Infrastructure/Http/Session/ReadOnlySession`. Ce middleware technique réutilise le magasin Laravel courant à la priorité d'initialisation de session, sans sauvegarde du contenu/âge des flashs, sans mise à jour de l'adresse précédente et sans cookies de réponse. Leurs groupes retirent les seuls middlewares natifs `StartSession` et `AddQueuedCookiesToResponse`, remplacés pour cette initialisation ; le déchiffrement des cookies entrants, ResolveSession, les contrôles d'accès et la protection CSRF ne sont pas retirés. Les révocations imposées par IdentityAccess restent effectives. Une future entrée de récupération peut réutiliser ce raccordement seulement si elle n'a pas à enregistrer de changement de session ; une entrée métier modifiant la session reste dans le parcours natif. Ainsi une lecture intercalée ne consomme pas le refus destiné à la redirection du formulaire et ne réécrit pas l'instantané d'un ancien compte.

Routes de gestion, toutes réservées au responsable : `GET /gestion/materiels` (`manageCatalog`), `GET /gestion/materiels/nouveau` (`catalog.create`), `POST /gestion/materiels` (`catalog.store`), `GET /gestion/materiels/{equipment}` (`catalog.show`), `PATCH` sur cette dernière (`catalog.update`). Création reçoit `name,category,description,totalQuantity,operationKey` ; édition reçoit `name,category,description,expectedVersion,operationKey`. Archivage et réactivation utilisent `POST /gestion/materiels/{equipment}/archivage` (`catalog.archive`) et `POST /gestion/materiels/{equipment}/reactivation` (`catalog.reactivate`), avec seulement `expectedVersion,operationKey`. Le responsable confirme l'archivage avant l'envoi. Une nouvelle intention vérifie toujours la version attendue ; si l'état demandé est déjà courant, elle produit un reçu sans mutation, incrément ni invalidation. Une répétition de clé/contenu conserve le reçu initial, même après une transition ultérieure. Les champs non admis sont refusés. Les succès Inertia redirigent vers la fiche avec `commandReceipt` sélectionné. Les lectures JSON privées sans cache sont `GET /gestion/materiels/lectures` (`catalog.page`), `GET /gestion/materiels/{equipment}/lecture` (`catalog.detail`) et `GET /gestion/materiels/operations?operationType=...&operationKey=...` (`catalog.operation`). La réponse de liste HTTP utilise `ManagementPageData` et ses `EquipmentSummaryData` : les mêmes champs sélectionnés que la référence, à l’exception de la description, réservée à la fiche. `ReadEquipmentAction::managementPage` demande directement la projection de résumé du repository : sa sélection SQL explicite ne charge pas la description et ne construit pas un `EquipmentData` complet avant de l’amputer. Cette action impose la capacité et la Policy de gestion, puis fixe cette audience indépendamment de celle fournie dans la requête PHP ; elle matérialise les résumés dans l’unité SQL de lecture autorisée. Filtres, tri nom/UUID et pagination simple restent communs aux deux projections. Les capacités PHP publiques continuent de fournir leur `EquipmentData` complet ; aucun texte enregistré n’est tronqué ou supprimé. Les réponses JSON Catalog émettent l’Unicode sans échappement superflu. Cette dernière route rend la forme `applied` ou `notEstablished` avec son reçu, ou la variante terminale `closed` définie ci-dessous, dans la portée du compte courant.

Pour les quatre commandes de fiche Inertia, `X-EPR-Operation-Key` porte la même clé UUID canonique que le corps et `X-EPR-Operation-Type` identifie la commande précise parmi les quatre familles ci-dessus. Ces en-têtes de visite suivent la redirection de même origine vers la fiche, sans ajouter de paramètres à son URL. La fiche valide les deux références ensemble puis relit le reçu acquis via `ReadEquipmentOperationAction`, également utilisé par `catalog.operation` : capacité responsable, acteur/atelier résolus au serveur et unité SQL de lecture. Le reçu appartient au compte courant et correspond à l’UUID de la fiche ; sinon `commandReceipt` vaut null. Référence mal formée : validation refusée. Ces en-têtes ne confèrent aucun droit. Les visites sans référence conservent le message de session compatible ; le client courant ne dépend pas de sa survie entre deux requêtes. La confirmation affichée indique le résultat acquis, y compris quand il a été relu ; le champ `replayed` conserve son contrat de reçu.

Le composant frontend public `PendingCatalogOperations` émet `absent(operationKey)` et `applied(operationKey, receipt?)`. Le premier argument reste la clé ; le second, facultatif pour compatibilité des consommateurs, transporte le `CommandReceipt` validé lors d’une vérification réussie. Le formulaire peut ainsi rapprocher sa version de base avec le résultat acquis sans perdre une saisie ultérieure.

Le navigateur conserve au plus vingt preuves minimales dans `sessionStorage` : portée de session hachée, type/clé, ressource/version éventuelles et empreinte du contenu. Le formulaire et son corps de reprise restent seulement en mémoire. Après une issue inconnue, vérifier avant toute reprise explicite avec la même clé et le même contenu ; après rechargement, aucun corps n’est reconstitué depuis une preuve. Les preuves disparaissent à la sortie ou au changement d’accès. Un stockage indisponible est annoncé ; les preuves restent en mémoire jusqu’à la fin de ce contexte ou au rechargement.

<a id="resolution-creation"></a>

### Résolution d'une création dont le contenu a été perdu

**Contrat adopté et entrée implémentée.** Le parcours ne concerne que `catalog.equipment.create`, pour le responsable courant et sa propre portée d'opération. La présentation légère et les conditions de l'action sont possédées par [EPR-T-063](../../cahiers-des-charges/technique/frontend-temps-reel.md) ; la décision atomique par [EPR-T-037](../../cahiers-des-charges/technique/transactions-etats.md#epr-t-037). Résoudre ne signifie ni recréer un corps perdu ni annuler un matériel déjà enregistré.

`POST /gestion/materiels/operations/cloture`, route `catalog.operation.close`, reçoit exactement `{operationType:"catalog.equipment.create",operationKey:UUID}`. Session, contexte serveur, capacité responsable, Policy et CSRF restent requis ; identité/atelier ne viennent pas du corps. La réponse est JSON `private, no-store`. Le GET `catalog.operation` demeure une lecture et retrouve aussi une clôture après perte de réponse. Ni navigation, ni reconnexion, ni lecture n'effectuent de POST automatiquement.

Les anciennes formes demeurent exactement `{status:"applied",receipt:CommandReceipt}` et `{status:"notEstablished",receipt:null}`. La variante terminale ajoutée est `{status:"closed",receipt:null,closure:{operationKey,operationType:"catalog.equipment.create",closedAt}}`, avec instant UTC de précision milliseconde. Cette preuve de clôture est une valeur distincte du reçu de succès. La clé/famille doivent correspondre à la demande et la génération d'accès rester courante avant tout retrait de preuve locale. Résultat inconnu, mal formé ou discordant : aucune clôture déduite.

Sous le même verrou d'intention, le serveur rend le reçu initial s'il est acquis, rend la clôture si elle existe, sinon enregistre cette dernière avant de la confirmer. Seule une issue terminale validée permet de retirer la preuve correspondante. Après `closed`, un nouvel envoi exige un nouveau clic et une nouvelle intention ; après `applied`, proposer la consultation sans nouvelle création ou navigation forcée. Attente, erreur, timeout, 429 et réponse perdue conservent l'incertitude et le blocage jusqu'à réception terminale. Une reprise explicite de la même clôture est idempotente.

Une création reçue après clôture est refusée avant comparaison d'empreinte et insertion, avec HTTP 409 et `operations.intent_closed` : paramètres publics vides, `outcome=notApplied`, `nextAction.kind=reload`. Le sens est « cette clé ne peut plus appliquer la création », pas « un matériel existant a été supprimé ». Aucun retry automatique ou diagnostic technique public. Le quota est de vingt POST par minute par acteur/atelier, sans quota supplémentaire sur la vérification GET ; le refus 429 garde les preuves et offre le délai natif Retry-After. Les autres bornes restent celles d'EPR-T-038.

Le code `operations.intent_closed` est déclaré par `IntentClosed::ERROR_CODE` dans `app/Infrastructure/Operations/IntentClosed.php`, exception de domaine attendue non signalée comme incident. `OperationRepository::acquire` le produit ; `CatalogIssueMapper` le restitue en HTTP 409 avec paramètres publics vides, `notApplied` et `reload`, en FR/EN. Les tests Catalogue HTTP et concurrence vérifient le refus tardif et son absence d'effet ; les fixtures de contrats qualifient séparément `OperationClosureData` et `ClosedOperationResultData`.

L'évolution du stockage et le retour compatible sont possédés par [EPR-T-012](../../cahiers-des-charges/technique/donnees-securite.md). Aucun matériel, version Equipment, notification Catalogue ou faux CommandReceipt n'est produit par la clôture. Les autres familles ne reçoivent pas ce nouvel état. Les clients qui ne reconnaissent pas la variante restent sans action dangereuse et nécessitent un rechargement ; leur coexistence doit être reçue avant une bascule concernée.

<a id="projections"></a>

## 4. Projections de présentation

Les pages de gestion Catalog disponibles présentent textes, état et total réel, avec un visuel de remplacement. Elles proposent archivage et réactivation, et signalent l’absence actuelle des engagements, disponibilités, images et du changement de total après création. La composition enrichie ci-dessous reste à WorkshopOperations.

Une liste est identifiée par ses critères appliqués et sa page. Les versions des matériels permettent de refuser une régression d'une référence encore connue, sans constituer une version globale de liste ni prouver l'appartenance au filtre. Pour la même identité de liste, une nouvelle prop Inertia déclenche une lecture de récupération sans remplacer directement la projection affichée, même si celle-ci est vide. La lecture reste protégée par son contexte, son identité et les invalidations reçues pendant son exécution. Un changement de recherche ou de page initialise sa propre projection ; précédent/suivant conservent les critères appliqués et une nouvelle recherche repart en page 1.

Catalogue emprunteur/agent : UUID, nom, catégorie, image publiée, quantité disponible, version de référence ; détail ajoute description. Gestion responsable ajoute total, réservé, remis et état actif/archivé. `equipmentVersion` ne classe pas les modifications d'engagement ; une disponibilité changée exige relecture, selon le [frontend](../../cahiers-des-charges/technique/frontend-temps-reel.md).

Liste personnelle : `requestId`, `reference`, `createdAt`, `state`, `requestVersion`, aperçu `{items:[{name,quantity}],remainingCount}` limité aux trois premières lignes, sans description. Tableau équipe ajoute l'identité de démonstration de l'auteur et `confirmedAt`, exclut brouillons. Ordres : création décroissante puis UUID décroissant pour liste personnelle ; confirmation croissante puis UUID croissant pour attente équipe ; confirmation décroissante puis UUID décroissant pour les autres états d'équipe. Détail : état/version, dates, lignes `{equipmentId,name,description,category,quantity}`, actions autorisées, motif, page d'historique et état du document nullable avant acceptation. Les textes viennent des instantanés dès confirmation ; dans un brouillon, ils viennent du Catalogue courant par lot, y compris pour identifier une ancienne ligne devenue non admissible, sans proposer cette référence à de nouveaux choix. Historique paginé : `id,action,actor:{actorId,displayName},occurredAt,requestVersion,reason` ; une ancienne composition se consulte séparément par sa version, jusqu'à 100 lignes. Aucun champ privé ne devient accessible par sa présence dans un type généré.

Contrat Reverb v1 : `eventId` UUID, `contractVersion: 1`, `authGeneration` entier, `type` et `payload` de l'union fermée suivante. La route par session détermine le destinataire ; un champ reçu ne choisit jamais ses droits.

| Type                   | Payload exact                                                                                                                                      |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `request.snapshot`     | `resource:{type:loanRequest,id}`, `projection:requestCore`, `version`, `data:RequestCoreData`.                                                     |
| `document.snapshot`    | `resource:{type:loanDocument,id}`, `projection:documentState`, `version`, `data:DocumentStateData`.                                                |
| `catalog.invalidated`  | `projection:catalog\|catalogManagement`, sans lignes ou identifiants privés.                                                                       |
| `requests.invalidated` | `projection:ownRequests\|teamRequests`, ou `projection:requestCore\|requestHistory\|documentState,requestId` seulement pour une demande autorisée. |

`RequestCoreData` : `reference`, `state`, `author:{actorId,displayName}`, `createdAt`, `confirmedAt`, `acceptedAt`, `items` historiques complets, `reason`, `allowedActions` ; dates non acquises/motif absent null, jamais champs omis. Actions fermées : `saveDraft`, `deleteDraft`, `confirm`, `replaceItems`, `accept`, `reject`, `cancel`, `handOver`, `return`, sélectionnées par droits/état. Historique/document sont actualisés séparément. `DocumentStateData` : `requestId`, `state`, `downloadUrl` nullable (route privée seulement si ready), `errorCode` public nullable, `canRetry` booléen. `version` est celle de la demande/document, jamais celle du Catalogue pour ses engagements. Snapshot ≤16 Kio ; sinon invalidation ciblée. Versions contradictoires/inconnues : relecture HTTP. Admission, buffer et récupération : [EPR-T-065 à 067](../../cahiers-des-charges/technique/frontend-temps-reel.md).

Les projections Catalog refusent, pour une même identité de lecture, une réponse Inertia ou HTTP contenant une version d’équipement inférieure à celle déjà connue. Une page de gestion est relue si un élément commun régresse ; les numéros d’équipement ne constituent pas une version globale de page ou d’engagement. La pagination réutilise les critères appliqués ; seule une recherche soumise remplace ces critères et repart en première page.

L’invalidation Catalog est produite après le commit extérieur dans la file `notifications`. Le job conserve seulement atelier et UUID d’événements ; les sessions sont sélectionnées puis immédiatement admises par les capacités IdentityAccess réelles. `catalogManagement` vise les responsables ; `catalog` vise les trois rôles. Une perte de publication n’annule pas la commande. Les erreurs du worker conservent leur cause native en mémoire et produisent un diagnostic sélectionné, y compris dans le fournisseur natif `failed_jobs`, sans SQL, bindings, corps ni jeton de session.

Le consommateur Catalog capture avant lecture et rapproche les invalidations reçues pendant celle-ci avant d’installer le résultat. Il refuse un résultat d’ancien contexte ou ancien filtre. Les lectures visibles sont regroupées à 100 ms, une par projection, deux simultanées au maximum contexte compris ; trois rapprochements immédiats au plus puis temporisation. Une lecture HTTP Catalog est bornée à 5 s. Le retour visible/réseau et la vérification périodique de 13 à 15 s récupèrent la projection sans rejouer de mutation. Une modification distante conserve les champs saisis et leur version de départ ; le chargement des valeurs actuelles demande une action explicite lorsque la saisie est modifiée.

## 5. IssueData et reprises

Forme exacte de la restitution sûre, DTO partagé `App\Shared\Errors\IssueData` : `errorCode: string`, `messageKey: string`, `parameters: objet`, `correlationId: UUID`, `outcome: notApplied|applied|unknown`, `nextAction: {kind,messageKey}` ; `fieldErrors` facultatif, objet indexé par chemin de champ, contenant des listes de `{messageKey,parameters}`. Les DTO de présentation partagés sont des valeurs PHP readonly avec sérialisation JSON sélectionnée et types générés ; ils ne nécessitent pas Laravel Data. Les paramètres vides se sérialisent en objet. Les paramètres sont sélectionnés par code, sans objet exception, message interne, trace ou SQL.

`nextAction.kind` appartient à `correctInput`, `reload`, `signIn`, `verifyOperation`, `retrySameOperation`, `contactStaff`, `contactManager`. Sa clé est exactement `actions.<kind>` dans FR/EN. `messageKey` principal est `issues.<errorCode>` ; repli `issues.operations.unexpected_failure`. Exemple actuellement livré : `catalog.content_conflict`, paramètres vides, `notApplied`, action `reload`. Ces indications ne déclenchent jamais automatiquement une mutation.

Le présentateur [explainIssue](../../../../resources/js/shared/i18n/issue.ts) accepte un message global connu et traduit avec des paramètres vides ; sinon il affiche le repli sûr, sans code brut ni diagnostic. Il conserve séparément un `outcome` reconnu et peut afficher une `nextAction` connue même si le message principal est rejeté. Un intitulé de repli ne constitue donc ni une autorisation de reprise ni une preuve de non-exécution. Les clés de champs `validation.*` et `identity.credentials` ne sont pas des codes IssueData.

Pour Inertia, préserver redirection, error bags et `errors` standard traduits ; la prop `issue` porte cette forme lorsqu’une issue globale est à expliquer. `validationPresentation:{locale,fieldErrors}` reprend seulement les clés/paramètres sélectionnés dans le même error bag, identifié par `validationErrorBag` (défaut `default`). Sa représentation JSON en session préserve les objets vides. Le client peut reformater les champs après changement de langue sans renvoyer la commande ; les erreurs natives sans mapping gardent le repli sûr et leur détail dans la langue de réception.

Un endpoint JSON déclaré rend l’issue sous `issue`. Les statuts et suites actuels sont précisés par les fiches, et ne se déduisent pas du seul code : 401 et 419 partagent par exemple le code d’authentification. Une validation Inertia conserve son parcours natif plutôt qu’un JSON 422 imposé. Le format admet `applied` et `retrySameOperation`, mais les mappers HTTP actuels n’émettent ni `applied` ni `retrySameOperation`. Aucune mutation n’est rejouée automatiquement après coupure.

### IdentityAccess - validation

`validation.invalid_input` adapte `Illuminate\Validation\ValidationException` dans `AccessIssueMapper::validation`. Le JSON non Inertia reçoit HTTP 422, `parameters:{}`, `outcome:notApplied`, `correctInput` et les `fieldErrors` sélectionnés. Chaque champ porte une clé de règle connue ou le repli `validation.unknown` ; seuls les paramètres numériques `min`/`max` pertinents sont conservés. Le contenu saisi, message natif et diagnostic ne deviennent pas des paramètres globaux.

Pour Inertia, le mapper prépare `validationPresentation`/`validationErrorBag` en session puis rend la main à la validation Laravel native. Le login refusé réutilise ainsi la clé de champ `identity.credentials`. Les formulaires et la présentation de champs consomment ces données ; le dictionnaire global ne contient actuellement pas `issues.validation.invalid_input`. Si cette enveloppe est expliquée comme message global, elle reçoit le repli ; les erreurs restent dans le JSON, mais explainIssue ne les affiche pas lui-même. Les formulaires utilisent leur parcours de champs ou validationPresentation. La correction de saisie est explicite ; une intention modifiée reçoit une nouvelle clé selon le contrat de commande. Le reporting reste celui du handler natif pour cette catégorie attendue.

### IdentityAccess - accès HTTP

`AccessIssueMapper::respond` reçoit une `Symfony\Component\HttpFoundation\Response` et un `Throwable`. Il choisit ces codes par statut déjà produit, sans correspondance exclusive avec une exception. Il laisse intactes les réponses de statut inférieur à 400 et les réponses JSON possédant déjà `issue` ou `props.issue`. Les causes natives telles que `Illuminate\Auth\AuthenticationException`, `Illuminate\Auth\Access\AuthorizationException`, `Illuminate\Database\Eloquent\ModelNotFoundException` ou `Symfony\Component\HttpKernel\Exception\HttpException` restent traitées par Laravel avant cette adaptation ; elles ne sont pas toutes assignées inconditionnellement à un code.

| Statut reçu | Code                                      | Effet déclaré et suite                                                                         |
| ----------- | ----------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 401 ou 419  | `identity_access.authentication_required` | `notApplied`, `signIn` ; confirmer l’accès courant avant toute nouvelle action.                |
| 403         | `identity_access.operation_not_allowed`   | `notApplied`, `reload` ; ne pas réinterpréter un refus de rôle comme une ressource disponible. |
| 404         | `identity_access.resource_unavailable`    | `notApplied`, `reload` ; même restitution sûre pour absent et privé inaccessible.              |
| 429         | `identity_access.rate_limited`            | `notApplied`, `reload` ; respecter le délai reçu, sans nouvelle tentative automatique.         |

Paramètres principaux vides pour les quatre codes. Le statut d’origine est conservé, avec JSON `issue` ou page Inertia `Error`, `private, no-store` et langue courante. Les dictionnaires IdentityAccess FR/EN et les consommateurs d’accès Catalog restituent ces indications ; aucun message interne, SQL, existence d’une autre ressource ou secret n’est envoyé. Ces mappings ne remplacent pas la décision d’autorisation ni le reporting natif des causes.

Le limiteur [CatalogServiceProvider::boot](../../../../app/Modules/Catalog/Providers/CatalogServiceProvider.php) produit aussi `identity_access.rate_limited` directement pour la clôture : vingt POST par minute/acteur/atelier, paramètres vides, `notApplied/reload`. Cette réponse conserve les en-têtes natifs dont `Retry-After` ; cette conservation n’est pas garantie par le mapper 429 générique. Le client de clôture transporte le délai jusqu’à l’attente affichée en FR/EN ; preuve et blocage restent conservés. Voir le [contrat de résolution](#resolution-creation).

### Operations - indisponibilité et repli HTTP

La déclaration de `operations.temporarily_unavailable` et `operations.unexpected_failure` appartient actuellement à `AccessIssueMapper::respond`. Le premier correspond au statut 503 reçu et propose `reload`. Le second est le repli pour tout autre statut d’erreur non couvert et sans issue JSON déjà sélectionnée, y compris un éventuel 400/405/422 natif ; il ne signifie donc pas exclusivement HTTP 500. Il conserve ce statut et propose `contactManager` pour une session staff/manager, sinon `contactStaff`.

Pour les deux codes, `parameters:{}` et la même règle d’effet s’appliquent : méthode HTTP sûre, ou statut inférieur à 500, donne `notApplied` ; méthode non sûre avec statut au moins 500 donne `unknown`. Dans ce dernier cas seulement, si l’attribut serveur `operationKey` est une chaîne, la suite devient `verifyOperation`. Une indisponibilité ne prouve pas à elle seule le rollback ou l’absence d’effet. Les clients relisent l’opération avant une reprise adaptée ; aucun de ces chemins n’émet `retrySameOperation` automatiquement.

La cause reste native, sans wrapper DomainError pour toute panne. Le statut 503 n’est pas une classification automatique de `Illuminate\Database\QueryException` : [RetrySqlUnit](../../../../app/Infrastructure/Operations/RetrySqlUnit.php) borne séparément les reprises de `40P01`/`40001` après rollback et hors unité extérieure ; une erreur SQL propagée peut encore recevoir un autre statut. Le handler/reporting conserve ses responsabilités. [bootstrap/app.php](../../../../bootstrap/app.php) sélectionne pour les erreurs SQL environnement, classe, SQLSTATE et corrélation vers le canal privé approprié, avec repli de collecteur sélectionné ; message SQL et bindings ne deviennent pas publics. La totalité des destinations et pannes de reporter n’est pas qualifiée par cette sélection.

JSON ou page Inertia `Error` restent privés sans cache ; les messages généraux Operations FR/EN et les indications d’aide ne publient pas le diagnostic ni ne créent un circuit de support. Preuves : [AccessBoundaryTest](../../../../tests/Feature/Modules/IdentityAccess/AccessBoundaryTest.php), diagnostic SQL sélectionné ; [BrowserContextTest](../../../../tests/Feature/Modules/IdentityAccess/BrowserContextTest.php), erreur publique sans diagnostic ; [presentation.spec.ts](../../../../resources/js/shared/i18n/presentation.spec.ts), repli d’un code brut inconnu. La combinaison code inconnu/suite reconnue est décrite par lecture du présentateur, pas revendiquée comme une matrice exécutée.

<a id="fiche-catalogue"></a>

### Catalogue - conflits, version et minimum

Les trois exceptions Catalogue de la carte implémentent `App\Shared\Errors\DomainError`, contrat limité à `errorCode()`. Elles peuvent sortir des capacités PHP publiques et des unités de commande ; le consommateur reste responsable de son unité extérieure. [App\Modules\Catalog\Equipment\Http\CatalogIssueMapper::render](../../../../app/Modules/Catalog/Equipment/Http/CatalogIssueMapper.php) adapte les DomainError seulement sur `catalog.*`/`manageCatalog`. Il sélectionne toujours des paramètres HTTP vides et `notApplied`, sans exposer le message interne. Le JSON reçoit 409 pour les conflits explicitement reconnus, sinon 500 ; Inertia reçoit une redirection avec erreurs Catalogue et `catalogIssue` sélectionnée. Les erreurs natives non consommées restent déléguées au handler.

- `catalog.content_conflict` : version attendue différente de la référence courante dans les services texte, état ou total. Catégorie refus attendu, `Illuminate\Contracts\Debug\ShouldntReport`. Suite HTTP `reload`, JSON 409 ; relire sans écraser une modification acquise. Les commandes de fiche et leur présentateur FR/EN consomment ce refus.
- `catalog.version_exhausted` : incrément impossible à la version maximale dans ces mêmes services. Incident sans marqueur ShouldntReport, soumis au reporting natif. Suite HTTP `contactManager`, JSON 500, `notApplied` ; ne pas réinitialiser la version. La fiche et les messages Catalogue FR/EN sont présents.
- `catalog.total_below_commitments` : [EquipmentTotalService::replace](../../../../app/Modules/Catalog/Equipment/UseCases/ReplaceEquipmentTotal/EquipmentTotalService.php) refuse un total inférieur au minimum protégé fourni au participant. Refus attendu ShouldntReport ; la propriété PHP readonly `minimumQuantity` est un entier. [ReplaceTotalWithinUnit::handle](../../../../app/Modules/Catalog/PublicApi/ReplaceTotalWithinUnit.php) est une capacité PHP livrée, sans transaction/reçu propre. La commande HTTP WorkshopOperations, son paramètre public `minimumQuantity` réservé au responsable et sa restitution dédiée restent à livrer. Si cette exception atteignait le mapper HTTP Catalogue actuel, elle recevrait paramètres `{}`, JSON 500 et `contactManager`, pas une restitution de minimum reçue. Aucun dictionnaire global FR/EN actuel ne fournit `issues.catalog.total_below_commitments`.

Les causes attendues n’acquittent pas une mutation : elles traversent l’unité responsable et la preuve d’absence d’effet dépend de cette transaction, pas du seul texte de l’issue. Aucun contenu de formulaire, modèle, minimum privé ou trace n’est ajouté aux paramètres HTTP. Preuves : [EquipmentManagementTest](../../../../tests/Feature/Modules/Catalog/Equipment/EquipmentManagementTest.php), versions périmées/exhaustion et absence de reçu ; [EquipmentStateTest](../../../../tests/Feature/Modules/Catalog/Equipment/EquipmentStateTest.php), état et total ; [EquipmentContractTest](../../../../tests/Feature/Modules/Catalog/Equipment/EquipmentContractTest.php), valeurs et unités participantes ; [EquipmentParticipantTest](../../../../tests/Integration/Modules/Catalog/Equipment/EquipmentParticipantTest.php), minimum refusé avec minimumQuantity=3 et ligne préservée.

<a id="fiche-intentions"></a>

### Operations - intentions

[OperationRepository::acquire](../../../../app/Infrastructure/Operations/OperationRepository.php) produit les deux refus DomainError ShouldntReport. `operations.intent_mismatch` signifie qu’un reçu de la même portée atelier/acteur/famille/clé possède une autre empreinte normalisée : la tentative divergente est refusée, le succès initial n’est pas nié et son reçu reste immuable. `operations.intent_closed`, déclaré par `IntentClosed::ERROR_CODE` et retourné par `errorCode()`, signale une clé de création déjà clôturée : acquire refuse l’appel tardif avant comparaison d’empreinte ou nouvelle écriture. Ce code d’erreur n’effectue pas lui-même la clôture. Il n’atteste ni suppression d’un matériel ni effacement d’un ancien succès.

Sur les routes de gestion, `CatalogIssueMapper::render` rend pour ces deux codes paramètres `{}`, JSON 409, `notApplied/reload`, ou la redirection Inertia de refus. Le message FR/EN ne divulgue ni contenu initial, ni empreinte, ni données d’un autre acteur. Après rapprochement du résultat durable, une création distincte exige une nouvelle intention explicite ; jamais d’écrasement du reçu ni de retry automatique. La fiche de [résolution d’une création](#resolution-creation) possède les formes `applied/notEstablished/closed`, leurs effets et la gestion des preuves ; ne pas confondre la clôture réussie avec l’erreur d’un envoi tardif. Preuves : [EquipmentManagementTest](../../../../tests/Feature/Modules/Catalog/Equipment/EquipmentManagementTest.php), reçus divergents et refus après clôture ; [EquipmentConcurrencyTest](../../../../tests/Integration/Modules/Catalog/Equipment/EquipmentConcurrencyTest.php), coordination et absence d’effet tardif.

<a id="fiche-notification"></a>

### Catalogue - diagnostic privé de notification

`catalog.notification_delivery_failed` appartient à `NotificationDeliveryFailed::diagnostic`, exception interne `RuntimeException` avec cause `Throwable` dans `previous`, sans DomainError. [PublishCatalogInvalidation::handle](../../../../app/Modules/Catalog/Equipment/UseCases/InvalidateCatalog/PublishCatalogInvalidation.php) lève cette exception après une panne de publication. Le job est après commit, trois tentatives et backoff 5/15 secondes ; certaines publications peuvent avoir réussi avant l’échec. La commande métier reste acquise, sans rollback ou IssueData déduit de ce diagnostic.

La projection privée contient seulement `errorCode`, `environment`, `workshopId`/`correlationId` UUID valides ou null, `exceptionClass`, `nativeCode`, `sqlState` si cause SQL, `causeFile` réduit au nom de fichier, `causeLine` et `causeMessageOmitted:true`. Elle omet message natif, SQL, bindings, corps, token et trace complète ; la cause en mémoire n’autorise pas leur export. `report()` signale sur le canal Catalogue avec repli sélectionné vers stderr si le collecteur échoue ; `__toString()` produit cette représentation pour les copies natives, dont `failed_jobs`. Conservation des diagnostics : [EPR-T-026/027](../../cahiers-des-charges/technique/donnees-securite.md). Le mécanisme des différentes copies doit être reçu séparément.

Les opérateurs habilités consomment ce diagnostic, sans statut HTTP, `nextAction` ou traduction publique. Une relance de job ne rejoue pas la commande métier ; la récupération des vues conserve les relectures bornées déjà définies. `catalog.notification_failed`, `database.failure` et `runtime.collector_unavailable` sont des libellés de logs, pas des codes d’issue supplémentaires. Preuves : [NotificationDiagnosticTest](../../../../tests/Feature/Modules/Catalog/Equipment/NotificationDiagnosticTest.php), cause native et vraie copie SQL sélectionnée ; les parcours privés de notification sont distincts des pannes du reporter ou de la conservation effective de chaque support.

### Entretien et portée des vérifications

À chaque ajout, retrait ou renommage, confronter la carte aux déclarations et mappings réellement atteignables, aux FQCN/méthodes existants et aux fiches ; vérifier conditions, paramètres, effets, langues et consommateurs. Une vérification ponctuelle des sources/liens complète cette revue, sans second registre runtime. Les contrôles actuels de tests et types ne constituent pas un contrôle permanent et exhaustif de cette concordance documentaire. Les résultats de vérification restent dans le suivi privé et les outils habituels.

Les preuves citées couvrent leurs cas reçus ; elles ne valident pas tous les transports possibles, chaque combinaison de repli, la panne de chaque reporter ou le cycle complet de chaque copie de diagnostic. Les contrôles CI obligatoires restent inchangés.

<a id="lots"></a>

## 7. Dépendances et raccordements communs

Chaque module possède ses migrations, ses routes et son provider. Les développements consommateurs s'appuient sur des fondations utilisables : IdentityAccess et contexte SQL, contrats partagés et génération des types, schéma Equipment et contraintes/FK nécessaires, capacités publiques Catalog. Ces dépendances n'autorisent ni réinstallation du projet ni préimplémentation des usages du module consommateur.

Catalog possède Equipment/Images, sans calcul des engagements. Lending possède demandes, engagements, historique et PDF. WorkshopOperations compose les capacités réelles Catalog/Lending pour les lectures enrichies et la modification du total ; ses pages et vérifications transverses ne deviennent pas des usages internes de Catalog.

Raccorder explicitement les providers dans `bootstrap/providers.php`, l'authentification/RLS, la navigation et la génération commune. Les contrats générés ont leurs sources chez chaque propriétaire, une seule génération commune et aucune édition manuelle. Coordonner les changements touchant ces raccordements. Pour une évolution de contrat partagé, identifier les consommateurs, examiner la compatibilité, faire approuver le changement puis actualiser tous les consommateurs concernés.

Les doubles temporaires respectent les contrats publics et restent bornés ; ils ne prouvent pas l'intégration des modules réels. Tout outillage personnalisé supplémentaire doit avoir un besoin et un périmètre explicites, sans être ajouté automatiquement à une contribution.

## 8. Qualification des dépendances

L'installation et les raccordements techniques ne qualifient pas les contrats, fixtures et fonctionnalités qui les consomment. Vérifier le contexte fiable, l'isolation sous le rôle réel, le schéma/FK et les fixtures nécessaires, les signatures/types et la génération PHP/JSON/TS sans SQL dans les transformations. Identifier la révision commune utilisée par les contributions dépendantes.

La recette intégrée appelle les capacités réelles Catalog, Lending et WorkshopOperations. La compatibilité Data v4/générateur v3 se qualifie sur les contrats ou la génération concernés selon [R04](../../../../.ai/rules/socle/04-contrats-dto-validation.md). Les [recettes](../developpement/qualite-et-recette.md) et la [qualification technique](../../cahiers-des-charges/technique/qualification.md) possèdent commandes, profils et critères ; leur rédaction ne constitue pas un résultat d'exécution.
