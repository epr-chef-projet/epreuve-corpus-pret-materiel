# Environnement - prêt de matériel

**Version 1.1.** Ce document possède les versions, paramètres et raccordements locaux. L'[installation](installation.md) possède l'amorçage et le cycle de développement ; les [contrôles](qualite-et-recette.md) et le [contrat de livraison](../exploitation/collaboration-livraison.md) possèdent leurs recettes respectives. Les [contrats de données](../../cahiers-des-charges/technique/donnees-securite.md) possèdent les privilèges et le contexte RLS.

Les services de développement sont HTTP, Vite/HMR, PostgreSQL, Redis, Mailpit, Horizon, Reverb et ordonnanceur. Le build fournit les assets de livraison et reste un contrôle de qualité. Les capacités métier, leurs tests et les mécanismes supplémentaires sont vérifiés dans les fonctionnalités qui les introduisent ; une réception d'installation ne les qualifie pas.

La contrainte PHP de `composer.json` et de `composer.lock` impose au moins 8.5.12 dans la branche 8.5. La construction Sail refuse une version antérieure ; la CI et la publication comparent aussi le PHP de livraison à la dernière publication officielle 8.5 et reprennent les scans actualisés. Ces exigences concernent tous les processus PHP, y compris les workers persistants.

Les runtimes PHP applicatifs doivent contenir les extensions requises par Laravel, les locks et les capacités utilisées, dont `pdo_pgsql`, `mbstring`, `intl`, `bcmath`, `fileinfo`, `openssl`, `zip`, `pcntl`, `posix` et le client Redis retenu ; Imagick/`exif`, fonts PDF et politiques ImageMagick se reçoivent avec les rendus concernés. Le runtime construit avant `vendor/` doit satisfaire les exigences du lock et des commandes d'amorçage ; il fournit ensuite le runtime applicatif de développement et se requalifie si ces exigences évoluent. Il reste distinct de l'image de livraison. Vérifier séparément extensions système et pilote PostgreSQL. `composer check-platform-reqs` complète la réception ; il ne prouve ni SQL, ni rendus, ni transport. Les références exactes des images d'amorçage, Sail, livraison, PostgreSQL, Redis et navigateur sont versionnées à leur introduction ; aucun digest d'exemple n'est une valeur utilisable.

## EPR-ENV-02 - Instances et adresses

Les instances de développement utilisent des copies distinctes dans le système de fichiers Linux WSL, sous des chemins choisis à l'installation. Terminal et éditeur ouvrent la même racine Git ; un autre dossier n'est pas une copie automatiquement synchronisée. Les identifiants `a`, `b` et `c` sélectionnent les paramètres ci-dessous.

| Instance | Projet Compose | HTTP canonique                | Vite/HMR               | WebSocket navigateur        | SQL du poste      |
| -------- | -------------- | ----------------------------- | ---------------------- | --------------------------- | ----------------- |
| `a`      | `epr-a`        | `http://epr-a.localhost:8081` | `epr-a.localhost:5171` | `ws://epr-a.localhost:8091` | `127.0.0.1:54321` |
| `b`      | `epr-b`        | `http://epr-b.localhost:8082` | `epr-b.localhost:5172` | `ws://epr-b.localhost:8092` | `127.0.0.1:54322` |
| `c`      | `epr-c`        | `http://epr-c.localhost:8083` | `epr-c.localhost:5173` | `ws://epr-c.localhost:8093` | `127.0.0.1:54323` |

C'est un profil local sur le poste ; chaque port publié est lié à `127.0.0.1`. Vérifier la résolution des trois noms `.localhost` vers cette adresse dans Windows et WSL ; si elle manque, faire préparer leur mapping local avec les droits nécessaires. Les hôtes distincts isolent aussi les cookies, dont le cookie CSRF natif : des ports différents sur `127.0.0.1` seul ne le feraient pas. Les URLs directes par IP servent aux sondes de santé. Le serveur navigateur d’essai utilise sa boucle locale, son cookie et son stockage réservés ; il ne reçoit pas les sessions de l’application locale. Recevoir `window.isSecureContext` et `crypto.subtle` depuis les navigateurs retenus pour le chiffrement de l'historique Inertia ; à défaut, refuser le profil et corriger son origine, sans désactiver cette protection. Le caractère local potentiellement fiable de `.localhost` n'est pas un profil de production distante. [Contextes sécurisés](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts).

Accès LAN, téléphone, TLS et autres origines demandent une adaptation qualifiée, sans remplacer les adresses internes. Depuis le réseau d'un projet : `pgsql:5432`, `redis:6379` et `reverb:8080`, avec `DB_HOST=pgsql`. Le processus de publication Laravel doit joindre la destination interne dans le profil concerné ; le navigateur du poste utilise l'adresse WebSocket de sa ligne. Le service HTTP Sail écoute sur le port interne 80 ; nginx de livraison utilise le port interne 8080. Redis n'est pas publié sur l'hôte par défaut.

Chaque projet possède son réseau, son stockage PostgreSQL, Redis, fichiers privés et journaux utiles. Les libellés du contrat `postgres-data`, `redis-data` et `private-files` désignent ces responsabilités ; le Compose de développement utilise `sail-pgsql` et `sail-redis`, avec préfixe du projet à vérifier. Raccorder les noms et chemins concrets à leur responsabilité, sans supposer un volume supplémentaire. Ne fixer ni `container_name`, ni nom global de volume/réseau, ni ressource externe partagée. Résoudre les noms effectifs avant toute opération : aucun nom court ne prouve l'isolation. Le profil de livraison doit posséder ses propres PostgreSQL, fichiers, Redis, sessions, clés et consommateurs. Les tests habituels utilisent la base `testing` dans le même PostgreSQL que l’application locale, avec fichiers et ressources d’essai séparés selon la [recette qualité](qualite-et-recette.md#isolation). Un projet supplémentaire est réservé à un besoin de qualification identifié ou à la CI.

Cette séparation protège contre les confusions ordinaires de cible, pas contre un acteur contrôlant le même moteur Docker ou administrant le poste. Un tel accès permet techniquement de monter d'autres volumes. Cette configuration ne qualifie donc pas une frontière de sécurité entre machines ou administrateurs hostiles. Les accès de contribution et d'exploitation sont distincts et limités aux habilitations applicables.

## EPR-ENV-03 - Configuration effective

Le Compose de développement, les exemples sans secrets, les runtimes/images et le mode d'amorçage définissent les raccordements de la base. Les profils d'essai et de livraison se vérifient séparément. L'amorçage et la garde Sail contrôlent racine, `EPR_INSTANCE`, identité Compose, fichiers sélectionnés, moteur Docker, utilisateur et montages ; une divergence est refusée avant l'opération. Contrôler aussi les valeurs héritées `COMPOSE_FILE`, `COMPOSE_PROJECT_NAME`, `DOCKER_HOST`, `DOCKER_CONTEXT`, `SAIL_FILES`, `APP_SERVICE`, `APP_USER` et la sélection `.env.<APP_ENV>` avant de démarrer Laravel.

| Entrées                                      | Contrat                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `APP_ENV`, `APP_URL`, `APP_DEBUG`, `APP_KEY` | Profils de développement `a`/`b`/`c`. `APP_DEBUG=false` par défaut dans les trois instances, clé stable propre à chacune. Un diagnostic debug se fait dans un profil isolé sans sessions partagées ; jamais de trace/exception native exposée aux utilisateurs. Aucun `key:generate` à chaque mise à jour.                                                                                                                                                                                                                                                                      |
| Connexions SQL                               | `DB_HOST=pgsql`, schéma `epr` déclaré dans les connexions app/auth/migration. Métier sous `app_role` restreint ; capacités IdentityAccess via `auth_lookup`, jamais accès global libre. Schéma créé/possédé par provisionnement/migration, application sans `CREATE`. Provisionnement `epr_provision`, migrations `epr_migrate` et sauvegarde `epr_backup`, credentials absents des processus HTTP/workers ordinaires. Préparer les rôles et fonctions étroites selon le contrat de données.                                                                                    |
| Redis et sessions                            | Connexions/espaces logiques séparés pour files, cache et sessions ; tous propres au projet. `SESSION_DRIVER=redis`, cookie `epr_a_session`/`epr_b_session`/`epr_c_session`, domaine non renseigné, cookie limité à l'hôte. Cookie CSRF Laravel natif, sans customisation concurrente. Métadonnées SQL des sessions et durée absolue de 2 h depuis connexion, sans renouvellement, selon données/sécurité ; l'existence de la session Redis reste requise, les métadonnées SQL seules ne restaurent pas l'autorité après perte/reset. Pas de purge globale pour réparer un test. |
| Reverb                                       | Écoute interne, destination de publication et destination navigateur distinctes ; clé publique exposable, secret serveur privé. Origines autorisées explicites, sans joker global.                                                                                                                                                                                                                                                                                                                                                                                              |
| Paramètres frontend                          | Projection publique à l'exécution : origine HTTP, hôte/port/protocole WebSocket et clé publique Reverb. Contrat de [frontend](../../cahiers-des-charges/technique/frontend-temps-reel.md), sans secrets ni compilation de la cible de livraison dans `VITE_*`.                                                                                                                                                                                                                                                                                                                  |

Les [rôles SQL et secrets de l'installation](installation.md#3-configuration-secrets-et-données) relient les libellés de responsabilité ci-dessus aux comptes `epr_bootstrap`, `epr_owner`, `epr_migrator`, `epr_app` et `epr_backup`. Le profil de base utilise debug désactivé, sessions Redis isolées et Redis sans publication hôte. Les capacités IdentityAccess et métadonnées SQL des sessions sont des exigences métier à implémenter et vérifier avec les parcours concernés ; elles ne sont pas prouvées par l'installation technique.

`env()` est réservé aux fichiers de configuration Laravel ; les processus consomment `config()`. Vérifier provenance des caches hors bootstrap Laravel avant tout premier démarrage, puis chargement et renouvellement utiles. Aucun `.env`, secret ou cache Laravel issu de la construction n'entre dans l'image de livraison. Une valeur publique compilée modifiée invalide le build ; modifier le `.env` serveur ne le répare pas.

## EPR-ENV-04 - Clone propre, sans `vendor/`

La commande `scripts/bootstrap --instance a`, avec `a`, `b` ou `c` comme identité explicite, initialise seulement les paramètres privés manquants du clone. Une copie supplémentaire de qualification peut utiliser `--run <nom>`. Les commandes Docker documentées rendent le runtime disponible avant `vendor/`, sans exiger PHP, Node, Composer ou Sail sur l’hôte.

Suivre l'[arrivée depuis un clone](installation.md#2-obtenir-un-clone-et-lamorcer) et la [séquence courante de `bootstrap`](installation.md#ce-que-fait-bootstrap). Cette procédure précise les commandes officielles pour la construction du runtime complet avant `vendor/`, l'installation depuis les locks, la maîtrise des scripts et plugins, la préparation SQL, les migrations et le build, puis le démarrage explicite par `./vendor/bin/sail up -d --wait --no-build --pull never`. La reprise après interruption appartient à la [procédure de mise à jour et de reprise](installation.md#5-mettre-à-jour-reconstruire-et-reprendre).

Ne pas remplacer cette recette par une acquisition initiale du kit ou un runtime d'amorçage partiel. Les dépendances, fixtures et fonctionnalités supplémentaires se vérifient dans leur périmètre propre ; elles ne sont pas requises par l'amorçage technique.

<a id="commandes"></a>

## EPR-ENV-05 - Commandes de base et contrats ultérieurs

Les commandes ci-dessous préparent la base et assurent son cycle de développement. Arguments obligatoires, absence de cible implicite et résolution contrôlée s'appliquent à chaque opération. Une commande n'installe pas un outil manquant à la volée. Toute capacité supplémentaire exige une conception et une attribution explicites.

| Commande ou contrat                                      | Effet et résultat attendu                                                                                                 |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `scripts/bootstrap --instance a`                         | Initialiser les paramètres privés manquants ; installation et migrations ont leurs commandes officielles dans la recette. |
| `./vendor/bin/sail up -d --wait --no-build --pull never` | Démarrer le profil préparé, attendre ses sondes, puis vérifier le fonctionnement.                                         |
| `./vendor/bin/sail stop -t 90`                           | Arrêter les services en conservant données, fichiers et clé.                                                              |
| `./vendor/bin/sail ps`                                   | Observer les services de la copie sélectionnée.                                                                           |
| `./vendor/bin/sail composer ci:check`                    | Exécuter les onze contrôles de base avec leurs codes natifs.                                                              |
| `./vendor/bin/sail artisan test --compact`               | Exécuter les tests PHP sur `testing` avec le rôle applicatif, sans autre installation.                                    |

La garde ciblée est décrite dans [l'installation](installation.md#4-travailler-au-quotidien). Les opérations de livraison utilisent une procédure réservée et ne sont pas fournies par le cycle Sail. Aucun fichier, secret ou volume de développement n'est copié automatiquement sur une cible de livraison.

Sail exécute PHP/Composer/npm/contrôles en développement après amorçage. Git et éditeur peuvent rester dans WSL hors conteneur. `scripts/bootstrap` utilise `2` pour l’usage invalide, `3` pour une précondition refusée et `5` pour un verrou incompatible ; les signaux restent des échecs. Sail, Docker et les contrôles conservent leurs codes natifs. Les codes contractuels `4` (contrôle échoué) et `7` (reprise manuelle) ne décrivent pas les sorties natives de cette recette ; vérifier tout autre profil dans sa procédure propre. Relire l'état après une interruption, sans annoncer un arrêt acquis.

<a id="processus"></a>

## EPR-ENV-06 - Processus et réception

Le profil de développement maintient HTTP, Vite/HMR, Horizon, Reverb et `schedule:work` avec les services explicitement supervisés. Le relais durable est raccordé avec les fonctionnalités qui l'utilisent ; aucun worker supplémentaire n'est improvisé. Le [contrat d'image](../exploitation/collaboration-livraison.md#image) est distinct de Sail : Chainguard/Wolfi PHP-FPM avec nginx-mainline et image commune aux cinq rôles HTTP nginx, PHP-FPM, Horizon, Reverb et ordonnanceur. Tous utilisent le même digest, sans montage des sources de développement ni outillage de développement/MCP. nginx écoute sur 8080 sans utilisateur root ; PHP et consommateurs utilisent un utilisateur applicatif non privilégié. Code/assets en lecture seule, écriture limitée aux chemins de cache/journaux/fichiers privés ; initialiser les droits sans `chmod 777`. Les signaux d'arrêt sont SIGQUIT pour nginx/FPM et SIGTERM pour Horizon/Reverb/ordonnanceur. Vérifier configuration, gestionnaire PID 1, réseaux, ressources et publication utile dans le profil de livraison. [Compose en production](https://docs.docker.com/compose/how-tos/production/).

Paramètres temporels proposés : timeout de chaque job au plus 60 s, Horizon 65 s, Redis `retry_after` 90 s ; trois tentatives au total et backoff de 5 puis 15 s, sans multiplication des retries entre couches. Le bail durable de 120 s et son propriétaire sont définis dans traitements/fichiers. Tout appel de bibliothèque et sous-processus respecte un budget inférieur au timeout du job ; vérifier `pcntl`, arrêt et absence de double effet. Ce choix suit l'ordre requis par [Horizon](https://laravel.com/framework/docs/horizon), sans prouver ses échéances réelles. La livraison possède son drainage de 90 s et son maintien fermé après dépassement.

Vérifier connexion SQL sous rôle réel, accès Redis isolé, démarrage/état et raccordements Horizon/Reverb, HTTP/assets et Vite/HMR, puis persistance et reproduction. Employer les commandes et diagnostics existants. Les preuves de job consommé avec résultat retrouvé, publication Reverb avec réception autorisée, ordonnanceur et relais sans doublon sont apportées avec les mécanismes concernés. Une preuve de démarrage ne qualifie pas ces parcours. L'éditeur utilise l'interpréteur Docker/WSL prévu et la publication SQL de la bonne instance. Observer quelle copie et quelle version servent réellement HTTP et chaque processus. Une sonde 200 ou `up -d` ne suffit pas.

Le panel HTTP Horizon et ses APIs de diagnostics sont désactivés/refusés explicitement pour les huit comptes produit et les visiteurs, dans tous les environnements. À l'initialisation, configurer et vérifier le refus des diagnostics exposés avec les outils disponibles ; la vérification des huit identités est apportée avec leur lot. Un callback de refus indépendant de `APP_ENV` et les routes concernées doivent être reçus ; la seule Gate `viewHorizon` ne prouve pas le refus en environnement local. Observation technique par CLI locale (`horizon:status`) et journaux privés, sans compte web d'administration globale ni Telescope de routine.

## EPR-ENV-08 - Mesures d'environnement

Relever CPU/RAM, limites WSL/Docker, emplacement des sources, images, Xdebug, navigateur et services actifs ; conserver une mesure courte du démarrage/affichage et une reproduction de l'installation, avec conditions et limites. La campagne ci-dessous vérifie les objectifs d'environnement ; sa description ne demande pas une plateforme de mesure personnalisée.

Dans cette campagne, mesurer séparément téléchargement/construction/installation à froid, démarrage avec images déjà présentes, puis édition → actualisation, contrôles courts et suite complète. Répéter chaque mesure quotidienne dix fois et rapporter médiane, p95, erreurs et conditions ; pour le bootstrap, conserver trois arrivées propres avec caches distingués, sans transformer trois essais en percentile fiable.

Commande de mesure à fournir et qualifier : `measure --profile environment --instance c --run <id>`, observations non destructives du poste et des stacks identifiées. Les profils applicatifs `volume`/`live` utilisent `--target qualified-test --run <id>` avec ressources d'essai résolues ; ils ne chargent ni réensemencent un environnement actif. Protocole et jeux sont possédés par qualification.

Comparer une instance de développement active, puis les trois instances ensemble, avec ressources au repos et en activité. Objectifs proposés : démarrage utile en 60 s avec images présentes, actualisation après édition p95 ≤ 2 s, absence de swap soutenu ou d'arrêt par manque de mémoire sur le parcours retenu. Coût de la suite : [qualité](qualite-et-recette.md#cout). Le profil applicatif de livraison vise au plus vingt sessions actives selon la [qualification](../../cahiers-des-charges/technique/qualification.md), pas vingt machines indépendantes. Toute mesure manquante demeure non qualifiée ; diagnostiquer montage, surveillance et ressources avant de changer la stack.

Procédures sélectionnées : [R20](../../../../.ai/rules/socle/20-environnement-dependances-qualite.md), [ENV-SAIL](../../../../.ai/rules/projet/environnements/laravel-sail.md), [R18](../../../../.ai/rules/socle/18-tests-preuves-acceptation.md) et [R19](../../../../.ai/rules/socle/19-performance-observabilite.md), dans le périmètre applicable du profil. Compatibilité déclarée, recette décrite et exécution restent distinctes.
